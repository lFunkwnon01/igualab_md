\section{Modelo de Datos}

El modelo de datos de Igualab se encuentra distribuido en dos bases de
datos PostgreSQL independientes, separadas por responsabilidad. La base
de datos transaccional almacena la información del negocio, la seguridad,
la trazabilidad y los resultados del análisis. La base de datos vectorial
almacena los fragmentos de los documentos y sus respectivos embeddings.

Ambas bases de datos son coordinadas por la aplicación FastAPI mediante
conexiones independientes. No existe comunicación directa entre las bases
ni claves foráneas físicas que crucen de una base a otra. La relación entre
sus registros se mantiene mediante identificadores UUID y referencias
lógicas administradas por la aplicación.

\subsection{Relaciones físicas y referencias lógicas}

El modelo utiliza dos tipos de relaciones:

\begin{itemize}
    \item \textbf{Relación física:} se implementa mediante una clave
    foránea entre tablas ubicadas dentro de la misma base de datos
    transaccional.

    \item \textbf{Referencia lógica:} relaciona registros ubicados en
    bases de datos diferentes mediante identificadores UUID. Su
    consistencia es validada por la aplicación FastAPI y no por una
    clave foránea del motor de base de datos.
\end{itemize}

\subsection{Entidades y relaciones del modelo}

Las principales relaciones del modelo son:

\begin{enumerate}
    \item Un usuario puede iniciar muchas sesiones y generar múltiples
    tokens de recuperación.

    \item Una empresa puede tener muchos documentos asociados.

    \item Un usuario con rol SuperAdmin puede registrar múltiples
    documentos.

    \item Un documento puede producir múltiples fragmentos en la base
    de datos vectorial.

    \item Un documento puede producir múltiples resultados de análisis
    GRI y múltiples sanciones.

    \item Cada resultado GRI referencia un código del catálogo GRI y
    conserva la cita textual que sustenta el hallazgo.

    \item Un Administrador puede realizar múltiples consultas al
    asistente RAG.

    \item Cada consulta puede tener múltiples citas asociadas con
    fragmentos documentales.

    \item Una empresa puede tener reportes de prospección asociados con
    diferentes años.

    \item Cada evento sensible genera un registro de auditoría asociado
    con el usuario responsable, cuando corresponda.
\end{enumerate}

Todas las relaciones internas de la base transaccional se implementan
mediante claves foráneas físicas. Las relaciones que involucran la tabla
fragmentos\_documento se implementan como referencias lógicas.

del negocio y la trazabilidad, mientras que la base vectorial se especializa
en almacenar embeddings y ejecutar búsquedas semánticas.

Debido a que las operaciones de ingesta afectan a dos bases de datos
independientes, FastAPI coordina el proceso y aplica operaciones de
compensación ante un fallo. Si la ingesta no se completa, la aplicación
elimina los fragmentos, embeddings o resultados parciales generados,
evitando que el documento quede procesado de forma incompleta.

\section{Diseño Arquitectónico}
La solución utiliza una arquitectura monolítica modular organizada en cuatro niveles principales: frontend web, API y servicios, procesos funcionales y datos. El frontend se implementa con React 18 y Vite; la API y la lógica de negocio se desarrollan con FastAPI y Python 3.13; el acceso a datos utiliza SQLAlchemy Async y AsyncPG. La persistencia se distribuye entre una base de datos transaccional PostgreSQL 16 con doce tablas y una base de datos vectorial PostgreSQL 16 con pgvector y una tabla. Las dependencias entre los niveles son descendentes y controladas por la aplicación.

FastAPI mantiene conexiones independientes con ambas bases de datos y coordina las operaciones que requieren información transaccional y vectorial. Las bases de datos no se comunican directamente entre sí. Sus registros se relacionan mediante referencias lógicas UUID validadas por la aplicación.

\section{Anexo}
\subsection{Problemas identificados del proceso actual (AS-IS)}
A partir del análisis del proceso actual (AS-IS) se identifican los siguientes problemas. El analista de Igualab debe buscar y descargar manualmente cada informe (memoria anual y/o reporte de sostenibilidad) de fuentes dispersas, lo que incrementa el riesgo de omitir documentos relevantes o descargar versiones desactualizadas. La revisión íntegra de documentos que suelen exceder las 100 páginas depende enteramente de su criterio individual, lo que genera variabilidad en la cobertura y profundidad del análisis entre distintas revisiones. No existe un catálogo estandarizado de indicadores GRI evaluables ni una metodología uniforme para asignar estados de cumplimiento, por lo que los criterios pueden variar de una empresa a otra. Una vez identificadas brechas, sanciones o hallazgos, el analista no registra la información en un sistema estructurado ni base de datos, ni hoja de cálculo, ni herramienta similar, por lo que los resultados quedan en su conocimiento implícito, sin posibilidad de consulta histórica, comparación entre empresas o trazabilidad. Tampoco se registra qué empresa revisó, en qué fecha ni con qué criterios, lo que impide validar la calidad del análisis o demostrar diligencia ante el cliente. La elaboración del documento de prospección se realiza en texto libre sin plantilla estandarizada, lo que genera formatos inconsistentes y omisión de información relevante. En conjunto, cada análisis parte de cero y no permite reutilizar resultados previos, comparar evolución año a año ni escalar el proceso a más empresas sin incrementar linealmente la carga de trabajo.
